版本：1.4（以用户截图为准的全局完整页面布局）  
日期：2026-11-15

## 1. 用途与目标

实况大屏是所有真实平台任务共同使用的执行观察与控制页面。用户应能直接看见：哪个账号、哪个任务、正在操作什么页面、处在哪一步、结果是什么，以及如何停止或处理登录验证。

主要使用者是不读代码和后台日志的桌面软件用户。成功标准是用户从页面上就能分辨“正在执行”“等待”“已停止”“画面断开”“结果待核验”。

本规定统一任务登记、自动打开、真实画面、运行轨迹、暂停/停止及结果展示。它不增加任何账号动作权限、发送额度或任务范围。作品发布等尚未完整接通的功能，只有具备实际执行能力后才能按本规范进入真实执行状态。

本文的“必须”均为开发与验收要求；“现状”仅描述本次查到的代码。没有验收证据的要求不得标记为已实现。

## 2. 本次问题与代码依据

用户反馈：启动真机评论点赞后，实况大屏没有自动打开。

检查发现三个接入缺口：

1. 评论点赞页的 `te()` / `confirmLive()` 调用独立真机启动通道后，只显示提示并刷新任务列表，没有自动切换到实况大屏。页面中存在 `$e()` 查看实况辅助函数，但真机启动路径没有调用它。
2. 评论点赞运行于 `CommentLikeService._workers`，真实任务通过 `registry.claim_account()` 占用账号；占用租约不会自动成为 `registry.active()` 中的运行实例。现有实体运行清单与预览查询主要合并 `registry` 和 `task_runner`，没有完整纳入这个独立服务。
3. 大屏保留了评论点赞统计的展示分支，但全局状态主要监听 `entity-leadgen-task-event`。独立点赞服务发出的是 `comment-like-task-event`，当前由评论点赞页局部订阅。因此不能仅凭有统计展示代码，就认为任务卡片、画面与轨迹已经接通。

这既包含自动导航缺失，也包含任务发现与事件接入缺失。单独加一个“跳转大屏”动作，仍可能进入空大屏。

本次只读检查时，桌面已位于大屏，评论点赞活动任务与实体运行清单均为空。这只能说明检查当时没有上述活动任务，不能还原用户此前点击的整段过程。

主要依据：

- `ui/assets/CommentLikeTasks-C67c1eAA.js`：启动、原生确认、局部事件订阅及查看实况辅助函数。
- `desktop/comment-like-launcher.js`：准确目标核对、原生确认、授权与启动。
- `backend/app/comment_likes.py`：独立运行线程、账号租约、真实/离线模式及专用事件。
- `backend/app/api/ipc_bridge.py`：`_rt_running_ids()`、`_live_preview()`。
- `backend/app/api/aggregate.py`：运行态聚合。
- `ui/assets/index-1pPBwPwk.js`、`ui/assets/Dashboard-QPICGlrw.js`：全局运行列表、事件、卡片及画面布局。
- `desktop/worker-surface.js`：同一个账号原生执行页在大屏与后台宿主间挂载、回收及渲染就绪确认；`desktop/live-preview.js` 保留坐标/缩放工具。旧截图查看页仅作历史兼容，不用于正式大屏。
- [位置与缩放交接](handoff-live-preview-layout-2026-11-15.md)、[画面闪烁交接](handoff-live-preview-flicker-2026-11-15.md)、[评论点赞交接](handoff-comment-likes-2026-11-15.md)。旧文档中的功能状态以当前代码与较新交接为准。

## 3. 全局使用范围

原则：凡是使用账号打开平台页面执行任务，都必须登记到同一个实况体系；纯配置、纯本地数据操作无需打开平台画面。

| 场景 | 是否登记实况 | 手动启动后的默认行为 | 大屏应展示的核心过程 |
|---|---|---|---|
| 评论点赞真机执行 | 必须 | 确认目标后自动打开并选中该任务，首帧就绪后才能点赞 | 视频、评论作者/正文、定位、已赞检查、点击、刷新复核、最终结果 |
| 评论获客真机任务 | 必须 | 自动打开并选中本次任务 | 关键词搜索、视频筛选、文案生成、发表评论、后续互动 |
| 线索采集 | 必须 | 自动打开并选中本次任务 | 搜索入口、当前视频/评论、筛选原因、线索入池及去重 |
| 养号 | 必须 | 自动打开并选中本次任务 | 进入视频、播放/切换、停留、动作、剩余时长与冷却 |
| 持续监控任务 | 必须 | 手动启动首次打开；后续轮询不重复切换页面 | 当前监控对象、最近检查时间、新内容、命中与等待倒计时 |
| 自动回复、批量跟进 | 实际使用平台页面时必须 | 手动启动自动打开；后台事件触发只更新全局状态 | 当前会话或对象、待发内容、提交及结果核对 |
| 吞评检测 | 桌面页面检测必须；纯接口检测登记状态即可 | 页面检测手动启动时打开；纯接口检测显示步骤和“无浏览器画面” | 检测账号、目标评论、查询阶段与检测结论 |
| 作品发布 | 接通实际执行后必须 | 用户确认实际发布后自动打开 | 素材、目标账号、填写、上传、提交及发布回执 |
| 弹窗内“读取评论并选择”等短时只读操作 | 必须登记账号占用及读取状态 | 保留当前选择弹窗，提供“查看实况”；不强制跳走导致选择流程中断 | 读取视频、已读条数、完成/失败、停止读取 |
| 排期、后台事件触发的真实任务 | 必须 | 登记卡片并提示状态，不抢当前页面或窗口焦点 | 与对应任务类型一致，显示触发来源 |
| 手动打开创作聚合、消息聚合、账号登录 | 使用各自平台容器 | 留在用户打开的模块；登录本身不计为业务任务运行 | 发生实际自动任务后再按对应任务类型登记 |
| 账号数据统计 | 有平台页面时登记；纯本地汇总无需 | 保留统计页面，提供实况入口 | 实际采集步骤或明确的“本地计算” |
| AI配置、任务设置、线索库编辑、导入导出、本地报表 | 无需 | 保留当前业务页面 | 使用对应页面进度，不制造平台执行窗口 |
| 离线模拟、演示 | 不进入默认真实运行区 | 留在独立测试入口，明确标记模式 | 模拟步骤与模拟结果，不显示为真实平台画面或真实成功 |

“真机模拟”是当前按钮用语，其行为属于真实账号操作。系统内部必须按 `live` 识别，不能按名称中的“模拟”归入离线结果。本文统一称其为“真机执行”。

## 4. 自动打开与任务启动顺序

### 4.1 手动启动真实任务

1. 校验任务配置、账号、占用状态和当前允许的动作范围。校验失败留在原页，给出具体原因。
2. 需要确认真实写操作时，先显示已有的准确目标确认。用户取消，不启动任务，不创建运行中卡片，不消耗尝试次数。
3. 后台建立本次运行编号并返回已接受状态；全局登记任务卡片，显示“准备执行”。重复点击返回同一次运行，不能启动第二次。
4. 前端自动切到实况大屏，定位本次任务和执行账号；多账号时定位首个实际开始的账号，并保留其余账号状态。
5. 将该账号实际执行器使用的原生网页直接挂入大屏容器，显示目标与当前阶段。真实写操作必须在本次运行的实际页面可见且完成渲染、身份校验及执行准备后才能开始。页面就绪仅是可观察性条件，不能替代原有账号、目标、额度与授权校验。
6. 执行、轨迹、统计和结束原因持续回写。任务完成后保留结束卡片及原页面；保留网页不等于任务继续执行。软件重启后不以旧图恢复已销毁的页面。

评论点赞已实现上述启动握手，保留原生确认的准确目标绑定和限次约束。隔离桌面已验证接线；正式账号的新增动作及平台留存仍需单独验收。其他模块按后续 P1/P2 逐项接入。

首帧失败时，未派发的平台动作保持未执行，显示“实况准备失败，尚未执行”，用户可明确重开；已经派发但结果不明时，必须显示待核验，不能按“启动失败”释放重试。

### 4.2 后台启动与用户主动离开

- 排期任务和自动回复后台触发时登记状态，不强制切换用户所在页面，也不把隐藏窗口强行弹到前台。
- 用户切到其他模块、最小化、隐藏到托盘或收起画面后，任务是否继续由原任务规则决定；画面的显示开关不改变任务权限、次数和运行状态。
- 手动启动时的首帧要求通过后，后台合法执行可继续；后续仅预览通道中断不直接判平台动作失败。执行窗口本身失效或账号/目标身份不符则按任务规则暂停或停止。
- 用户已在大屏时，只选中新增任务，不重载整个页面，不重建其他账号的执行窗口。
- 查看详情、打开日志、保存配置不触发自动执行或自动跳转。

## 5. 卡片、画面和运行轨迹

沿用现有前端设计：顶部账号与任务状态卡，下方视频窗口，右侧可展开运行轨迹；继续支持排列、放大和收起。不得为了新模块另做一套不同的大屏。

每张任务卡必须能读到：业务类型、任务名、执行账号昵称、运行模式、触发来源、当前阶段、开始/结束时间、进度、真实结果摘要，以及查看画面/日志/停止入口。

卡片身份以“任务类型 + 任务编号 + 本次运行编号 + 账号编号”区分；账号视图可复用，但结束事件、日志与统计必须归属本次运行。同一账号前后两次任务不能相互覆盖。同一账号不能被多个任务同时控制。

大屏中的平台网页必须与执行器持有完全相同的 webContents。禁止另开同网址页面、定时同步网址、截图镜像或 Canvas 重绘替代原生执行页。登录弹窗与大屏复用同一个账号页面及既有会话分区；切换容器只移动页面，不导航、不刷新、不重建登录态。

右侧轨迹按阶段记录时间、目标、动作与结果，例如：

> 读取目标 → 找到准确评论 → 检查未赞 → 提交一次点赞 → 收到平台回执 → 无缓存刷新复核 → 成功 / 待核验。

只有后端实际发生的阶段才能写入轨迹。打开大屏不能顺带触发第二次搜索、重新导航执行页或重新提交动作。

布局继续遵守已有规则：CSS坐标由主进程按主界面缩放转为原生边界；网页仅占自己的内容容器，不覆盖导航、日志或确认弹窗。展开轨迹、调整大小、缩放及显示器变化后重新核对边界；远程平台页缩放不得影响本地主界面。

## 6. 三种状态必须分别显示

| 状态维度 | 示例 | 判定依据 |
|---|---|---|
| 任务状态 | 准备、排队、执行、等待、暂停、停止中、已停止、已完成、失败、中断 | 当前执行服务及本次运行记录 |
| 页面状态 | 准备页面、原生页已嵌入、后台已收起、加载中、页面失效、无浏览器页面 | 原生页面身份、宿主、可见性及渲染状态 |
| 平台动作结果 | 未执行、提交中、成功、已操作而跳过、明确失败、结果待核验 | 对应动作的可靠证据与持久化结果 |

必须分别处理：

- 等待模型：显示“生成文案中”及耗时，保持目标上下文；不能伪装成视频正在操作。
- 等待间隔/冷却：显示原因与倒计时；执行窗口空闲不等于任务结束。
- 等待登录/验证码：阻止该账号后续动作，显示“需要处理”及明确入口，通知一次，不循环弹窗；用户完成后重新校验账号、任务和额度。不得自动绕过验证。
- 页面加载失败或渲染进程退出：显示具体错误；任务状态仍从执行服务读取，不能据此编造成功或失败，也不能用旧截图盖住故障。
- 任务结束：卡片标明原因、最终结果与结束时间。原页面可以保留，但不以页面视频仍在播放证明自动任务仍运行。
- 服务断连或重启：显示状态核对中；原运行无人接管时归为中断。对结果不明的已提交动作保留待核验，不恢复自动提交。

## 7. 显示控制、暂停与停止

- “关闭/收起画面”将原生页移回后台宿主；“停止任务”控制执行。按钮文案与提示必须明确区分。
- 原生页面支持正常鼠标、键盘和滚动，允许在同一账号实际页面处理登录与平台提示。人工接管前通过现有暂停/停止入口结束自动控制，并以执行器确认结果为准；不另开一张同网址页面充当人工处理页。
- 用户打开确认框、下拉菜单或设置弹窗时，原生图层必须让出位置，不能遮挡；取消或关闭弹窗后恢复正确的预览布局。
- 只有执行器支持安全暂停并能确认暂停生效时才展示“暂停”。否则提供“停止”，不得仅改变页面徽标却让执行器继续运行。
- 暂停必须禁止后续动作，展示“暂停中”直到执行器确认；恢复前重新核对目标、登录态和额度，不重新提交暂停前结果未明的动作。
- 停止发往正确的业务服务，精确绑定任务、运行与账号。评论点赞必须进入其专用停止链路，不能发送成普通采集任务停止。
- 发出停止后立即显示“停止中”，取消待派发动作及可中断等待；收到执行器确认后才能显示“已停止”。已经提交的平台动作不能写成已撤回，仍需核对结果。
- 某账号停止不影响其他账号；“停止全部”必须明确范围，并逐个报告停止结果。

## 8. 运行发现、事件和历史的统一约定

全局实况必须纳入所有实际执行服务，包括 `registry`、`task_runner`、独立评论点赞、短时评论读取，以及未来的自动回复/批量跟进/发布服务。允许保留各自执行器，通过统一聚合适配器向大屏提供一致状态；不要求为统一展示重写所有业务执行器。

统一快照至少包括：任务类型与编号、本次运行编号、账号、模式、触发来源、当前阶段、任务状态、画面能力与引用、更新时间、动作统计、结束原因、可用控制能力。

统一事件至少包括：已登记、阶段改变、统计改变、需要用户处理、停止确认、运行结束。事件必须绑定运行编号并能去重；前端页面卸载不应使全局任务状态丢失。评论点赞专用事件需要接入全局，不能只由点赞页订阅。

必须用当前执行服务与账号租约核对真实活动状态。历史数据库中一个孤立的 `running` 字段不能证明正在执行；单个查询失败也不能被当成空列表，进而把真实任务清空。

刷新或重进大屏时先取当前快照，再衔接事件，避免恢复期间遗漏开始/结束。毫秒级短任务也必须留下运行记录与结束摘要，不能因轮询未赶上而完全消失。

离线、演示和真实模式保持独立。模拟计数不得进入真实结果；平台回执成功但未达到该动作的最终确认条件时，展示待核验。评论点赞仍要求回执、即时状态及刷新后留存同时满足，新增成功才加1。

## 9. 后台、资源与隐私

- 使用原生网页自己的渲染与输入，不再定时截图，也不以固定5帧/秒限制平台视频。
- 收起画面后，页面回到常驻隐藏宿主，保持视口、缩放、DOM和登录态，后台任务可以继续；回到前台或点击“查看实况”后挂回原页面，不触发新的搜索或重新打开推荐流。
- 任务结束后默认保留摘要及已有页面，至少30秒内不自动消失；用户明确关闭可以提前移除。历史记录持续保存；退出软件后不保证已关闭网页恢复。
- 多账号窗口只展示各自执行画面，重排不切换业务目标；预览窗口数量和可见性不改变执行并发上限。
- 不在日志、截图文件名或卡片中输出Cookie、Token、密钥。实况不默认持续录屏；导出证据需明确范围并对敏感内容脱敏。截图失败时标明失败，不能使用旧图片冒充。

## 10. 验收目标与场景

以下时间是后续实施目标，不是本次已测结果：启动被接受后1秒内出现准备卡片；真实执行页可采样后3秒内显示首帧；停止控制1秒内发送至执行器；普通可中断等待2秒内收到停止确认。平台加载超时、在途提交及其他无法立即取消的步骤必须显示真实原因，不能为了满足时间指标伪报完成。

| 编号 | 验收场景 | 必须看到的结果 |
|---|---|---|
| A01 | 取消真机点赞原生确认 | 留在原页面；无新运行、无授权消耗、无点赞 |
| A02 | 从点赞页确认新目标 | 自动进入大屏；正确账号、准确评论、首帧和步骤可见；最多一次提交 |
| A03 | 大屏准备失败或首帧超时 | 未派发动作不执行；有明确失败阶段；不出现虚假成功 |
| A04 | 点赞回执成功但刷新后未保留 | 显示待核验，真实成功0；结束原因与详情一致；禁止自动重试 |
| A05 | 任务很快结束 | 即使没有赶上轮询也保留结束卡片和记录，不能只看到空屏 |
| A06 | 搜索获客、采集、养号、监控分别手动启动 | 各自出现正确任务卡片和真实执行画面，不串任务、不串账号 |
| A07 | 在选择评论弹窗内只读采集 | 弹窗和已选项保留；可查看实况；不额外启动点赞 |
| A08 | 排期或后台事件启动 | 自动登记但不抢页面；进入大屏后能恢复对应任务 |
| A09 | 点击停止、取消停止、连续点击停止 | 正确服务收到对应控制；取消不停止；重复控制不产生第二次平台动作 |
| A10 | 关闭预览、切页、托盘隐藏再回来 | 状态与执行一致，恢复当前画面；无重新提交或反复刷新业务页 |
| A11 | 平台要求登录或验证码 | 对应账号停止后续自动动作；给出处理入口；其他账号按原任务继续 |
| A12 | 调整缩放、窗口大小、展开轨迹、打开确认弹窗 | 画面不遮挡，边界正确，不闪白，不修改主界面缩放 |
| A13 | 实时事件断连、服务重启或旧事件晚到 | 状态提示清楚；本次运行不被旧事件覆盖；不确定动作不自动重试 |
| A14 | 离线模拟成功后打开默认实况与详情 | 不增加真实成功，不展示假平台画面；模式标记一致 |
| A15 | 两个账号同时运行及同账号重复启动 | 两个账号各自展示；同账号占用冲突明确拒绝或排队，不抢执行页 |

每项验收要记录桌面版本、任务/运行、账号脱敏标识、起止时间、观察结果和证据来源。离线验收只能证明接线、状态和边界；真实账号动作必须另有对应平台证据。本文编写过程没有启动新点赞或其他平台写操作。

## 11. 实施顺序与交付边界

P0：先补评论点赞的全局运行发现、事件、卡片和准确停止路由，再补确认后的自动导航及首帧启动握手，最后核对统计与结束摘要；必须一起验收，避免只跳转到空屏。

P1：统一评论获客、采集、养号、监控、读取及其他已经接通的任务；验证跨页面恢复、后台触发、账号占用、错误状态与短任务留痕。保持现有界面布局及原生坐标、缩放处理。

P2：在各自执行能力接通时，将发布、自动回复及新增平台任务纳入同一约定；优化多账号布局、资源策略与证据导出。未接通能力显示未接通，不制造正在执行卡片。

开发最小交付条件：用户在评论点赞页启动一条受限真机任务后，能够自动看到正确账号与目标的真实现场，并在同一处查看阶段、停止及最终结果；刷新或重进后仍可核对同一次运行。

已知风险包括独立服务遗漏、晚到事件串运行、预览图层遮挡、短任务结束太快和多账号资源开销。对应控制分别为统一聚合、运行编号绑定、复用现有边界机制、持久化结束摘要与可见窗口节流。

本轮先交付全局规定及 P0 评论点赞实现。后续模块按 P1/P2 推进，不将已有局部接线视为全局验收完成。
