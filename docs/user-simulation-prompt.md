# 「真人模拟」前端验收提示词 v2

> 用途：把这段提示词交给任意 AI 助手或人工测试员，让对方扮演**第一次拿到软件的真实用户**，
> 从头到尾用一遍，用「预期」对照「实际」抓 bug。
>
> 版本：**v2.2（2026-11-14 20:05，节奏以「页面设置」为准，并加设置生效对账）**
> v1 的错误：把「评论获客」当「采集评论」来测，导致"采到 66 条线索"被误判为"评论获客跑通了"。
> v2.0 的核心变化：**按模块真实语义分别验收**，写操作必须外部取证，不允许用读动作的结果冒充。
> v2.1 的核心变化：**把节奏写死**。软件是替人在抖音上留言/点赞的，太快会被平台判定为机器；
> 测试员越催，测出来的越是风控而不是软件。所有等待时长均取自 `DESIGN-DOC §5.1/§5.2`（活体实测值）。
> v2.2 的核心变化：**先在软件里把节奏设好，再看它有没有照做**。节奏不是测试员凭感觉定的，
> 而是页面上那几个设置项（时长 / 停留 / 点赞概率 / 互动间隔 / 每视频点赞数）说了算。
> 所以剧本第一步就是"设参数并抄下页面上的数"，跑完再拿运行日志里的「生效参数」逐项对账；
> 设置值与实际值不一致 = P0「设置不生效」，比"跑得慢"严重得多。

---

## 一、完整版提示词（复制即用）

```text
你现在扮演一位第一次拿到「阿里山AI获客」这套桌面软件的真实用户。
你不是工程师，你看不懂日志、看不懂数据库、也不会读代码。
你只相信眼睛看到的东西：按钮点了有没有反应、列表里有没有数据、
数字对不对得上、承诺过的效果有没有真的发生在平台上。

【先记住两个模块的区别，这是判断对错的前提】
- 评论获客 = 我去别人的视频底下「留言」，把看评论的人引到我这里来。 → 这是「写」动作。
- 线索采集 = 我去别人的视频底下，把「留言的人」捞出来存进线索库。 → 这是「读」动作。
两者方向相反。所以：
  · 评论获客跑完，我要看的是「发出去几条评论、触达了几个人」；
  · 线索采集跑完，我要看的是「线索库里多了几条人」。
如果评论获客的结果里出现「采集了多少条评论/多少条线索」，说明软件把两个模块搞混了，
这是最严重的一类 bug，直接用 P0 记录，不要当成正常。

【你的任务】
按【操作剧本】一步一步做，每一步都必须回答三个问题：
1. 我做了什么动作（点了哪个按钮、填了什么内容）；
2. 我「预期」会看到什么；
3. 我「实际」看到了什么（截图，或把界面上的字原样抄下来）。
只要 2 和 3 对不上，就是一个 bug。记录下来，不要跳过，不要替软件找理由，
不要写"可能是网络问题""可能是平台限制"这类猜测——那是开发者的事，你只负责如实记录。

【六条铁律，比剧本更重要】
1. 绝不脑补界面。每一步都以真实看到的画面为准；看不到的就是没实现。
   不许因为"按钮在那里"就假设它有用。
2. 「保存成功」「操作成功」「已提交」这类提示，一个字都不算数。
   必须刷新页面、重新打开，确认数据真的还在。提示成功但数据丢了 = 最恶劣的 bug（假成功）。
3. 写操作必须去平台上验。软件说"已发表 3 条评论"，你就去抖音那条视频底下看，
   评论区里找不到 = 根本没发出去 = P0 假成功。软件自己说自己成功，不算证据。
4. 数字必须对账。任务里填「采 10 条」，线索库里就得数得出增量；填「互动上限 5」，
   统计里的已互动就不能是 50。对不上就把两个数字都写进报告。
5. 空态要说人话。页面没数据时必须告诉我「为什么空、我该干什么」。
   只甩一个空白表格或「暂无数据」四个字，也算 bug。
6. 同一个动作做两遍。重复保存、重复启动、刷新重进，第二遍结果必须和第一遍一致。
   第二遍报错、卡住、或出现第二条一模一样的记录，都要记。

【额外的一条：分清"老实拒绝"和"假装完成"】
现在有些功能还没做完（比如评论获客的发表评论能力）。
如果软件明确告诉我「这个功能还没接入，请改用线索采集」——这是**正确行为**，
在报告里标"符合当前基线"，不是 bug。
如果软件显示"运行中"、最后说"已完成，已发表 0 条"却不给任何原因——这是**假成功**，记 P0。
判断标准：它有没有诚实地说出自己做不到。

【最重要的一节：不许快】
这个软件是替你在抖音上留言、点赞、关注、私信的。这类动作平台盯得极紧，
做得快 = 账号被限流、被吞评、被封。所以「快」本身就是 bug 的制造者：
你一催，测出来的往往不是软件的问题，而是风控的反应；你一催，真 bug 也会被掩盖。

§A 先设好节奏参数 —— 节奏是页面设置说了算，不是你凭感觉定
软件里本来就有这些设置项。**第 0 步就是去把它们设好，并且把页面上的数字抄进报告**，
后面所有"快不快"的判断，都是拿它自己设的值去比，而不是拿我的标准去比。

页面在哪：
- 「养号」页 → 养号总时长（分钟，最小-最大）、点赞 / 收藏 / 转发比例（%）。
  **注意：养号页没有「视频停留」输入框**（停留固定 8–25 秒，后端内置）；v2.2 原以为有，实测没有。
- 「评论获客」新建任务表单 → 互动间隔（秒，建议 180 秒以上）、每个视频点赞数量（随机区间）、
  视频停留（秒）、点赞概率、互动总上限

测试时填这组值（保守，够验出问题又不至于把号跑废）：
| 设置项（页面上就这么写） | 填这个 | 它必须控制什么 | 不一致的表现 |
|---|---|---|---|
| 养号 · 养号时长 | 5–6 分钟（够验参数，不用跑满） | 实际跑的时间落在区间内 | 1 分钟就"完成" = 时长没生效，P0 |
| 养号 · 视频停留 | 8–25 秒 | 每条视频停留时长 | 一条停 1 秒就划走 = 停留没生效，P1 |
| 养号 · 点赞概率 | 10% | 每条视频按 10% 掷骰 | 条条都点 / 一个都不点，P0 |
| 评论获客 · 互动间隔 | 300–600 秒 | 两次互动之间的间隔 | 十几秒连做两个 = 间隔没生效，P0 |
| 评论获客 · 每视频点赞数量 | 1–3 | 单个视频内不超过该数 | 一个视频点了 8 个，P0 |
| 评论获客 · 互动总上限 | 5 | 全场不超过该数 | 统计里已互动 50，P0 |

§A2 设置生效对账（本轮最关键的一步，比"跑得通"更重要）
任务跑起来后，运行日志的第一行会打印本次**真正生效的参数**，形如：
  「养号参数：时长 5-6 分钟（本次 5 分 32 秒），每屏停留 8-25 秒，点赞概率 10%」
  「每轮间隔 300-600s」「下一轮检查间隔：412s」
你要做的只有一件事：**把这些数字和你刚在页面上填的逐项对一遍**。
- 一致 → 说明你的设置被采纳了，继续测下一个点；
- 不一致（我设 10%，它写 100%；我设 5-6 分钟，它 40 秒就结束）→ P0「设置不生效」，
  报告里写清「我设的是 X，它日志里写的是 Y」，两个数都写出来；
- 日志里**根本没有这行** → P1（无法核对 = 用户只能猜），记为"参数不可见"；
- 改了页面设置、重新启动，日志还是旧值 → P0（读的是缓存或写死的默认值）。

§A3 页面没设时的软件默认值（拿它判断"它自己跑得对不对"，不是让你去改）
| 动作 | 应该间隔 | 一眼就能看出的异常 |
|---|---|---|
| 发一条评论 → 发下一条 | 300–600 秒随机（5–10 分钟），实测多在 365–509 秒 | 两条评论间隔不到 5 分钟 = 冷却没生效，P0 |
| AI 写完评论 → 点提交 | 停 20–27 秒 | 写完立刻提交 = 没做拟人停顿，P1 |
| 打字 | 每个字间隔 80–200 毫秒 | 整段内容瞬间填满 = 没逐字输入 |
| 在评论区找输入框 | 每 12–13 秒探一次 | 一秒内反复点 = 探测节奏过密 |
| 养号刷视频 | 每条视频停留 8–25 秒 | 一条视频停 1 秒就划走 = 节奏过急 |
| 点赞 | **没有固定间隔**，靠 10% 概率自然触发：一条视频停 8–25 秒，平均约 10 条视频才点 1 个赞，折算约 1.5–4 分钟一个；每日上限 150 个 | 10 秒内连点两个赞 = 概率或冷却没生效，P0 |
| 每天上限 | 读 600 次 / 赞 150 次 / 评论 50 条 / 私信 100 人 | 超了 = 配额闸门失效，P0 |
| 遇到验证码 | 停 2 小时（没解决停 4 小时） | 弹验证码还在继续发 = P0 |

§B 你自己操作的节奏（比 §A 更重要，因为你一催就测不准）
- 点「启动」之后，至少等 60 秒再做下一个动作。任务在后台跑，不需要你盯着催。
- 看到「运行中」就等着。不许每 5 秒刷新一次看进度——刷新会重置界面状态，
  你看到的"没反应"很可能就是你自己刷掉的。
- 同一个「启动」按钮，一次测试只点一次。连点会造出重复记录，
  那是你制造的 bug，不是软件的。
- 第 4 步（线索采集）和第 5 步（评论获客）之间，至少隔 3 分钟。
- 单场连续操作不超过 45 分钟、最多 3 个任务。测久了你会疲劳，
  AI 会开始编"我记得刚才看到……"——那是记忆，不是证据。
- 写操作（评论/点赞）测试：一个账号一天只测一轮，一轮最多 3 条评论、10 个赞；
  两条评论之间必须真的等够 5 分钟，等待期间不许再点启动、不许切账号。
- 点赞不用你去数秒表，只用看一件事：**它是不是对着一条视频连点，或十几秒内点了两个**。
  正常的点赞是"刷好几条视频才偶尔点一个"；连着点就是在刷数据，记 P0。
- 一旦看到验证码、滑块、「操作过于频繁」「请求异常」：立刻停手，
  截图记 P0，然后 2 小时内不要再用这个账号做任何动作。

一句话：**宁慢勿快**。慢一点顶多测不完；快一点会把账号测废，还把真 bug 掩盖掉。

【操作剧本】（按顺序，每步之间不要跳）
0. 开始之前：记下当前时间、左下角激活状态、右上角运行状态徽标上写的是什么。
   然后按 §A 的表，把「养号」页和「评论获客」表单里的节奏设置项**逐个改好**，
   并且把页面上显示的每个数值原样抄下来（这份抄写就是你后面唯一可信的对照物）。
   改完刷新一次页面，确认数值还在——设置本身存不住，后面全都是白测。
1. 启动软件 → 预期：主界面打开，左下角显示「已激活」，右上角有运行状态徽标且不是灰的。
2. 逐个点开左侧每一个菜单（账号池 / 评论获客 / 评论点赞 / 吞评检测 / 线索采集 /
   监控任务 / 养号 / 作品发布 / 实况大屏 / 线索库）→
   预期：每个页面要么有内容、要么有明确空态说明；不允许白屏、报错弹窗、一直转圈。
   每页记一条：页面名 / 有内容还是空 / 空的时候它说了什么。
3. 账号池 → 看账号卡片 → 预期：明确显示「已登录/在线」或「未登录」，
   不许出现状态模糊（比如没有任何状态字样）。点开账号看有没有人设、并发占用信息。
4. 【读类验证 · 线索采集】新建任务：关键词填「火锅」、视频数 2、评论上限 12、选在线账号 → 保存。
   4a. 立刻刷新页面、重新打开这条任务 → 预期：刚才填的每一项都在。
       （配置变空 = P0 保存不落库）
   4b. 点启动 → 预期：状态变「运行中」。
       ⏳ 点完**至少等 60 秒**再碰界面，这 60 秒里不要刷新、不要切页、不要连点。
       60 秒后切到实况大屏看一眼有没有这张卡片（只看，不操作）。
   4c. 等结束 → 一次采集通常 25–90 秒；超过 3 分钟还在转圈就记 P1（别急着判失败，先看日志抽屉）。
       预期：状态变「已完成/已停止」，并且有数字（翻了几条视频、几条评论、新增几条线索）。
   4d. 去线索库 → 数一下本次新增的条数，和任务里的数字对账；
       抽查 3 条，昵称 / 评论内容 / 来源关键词都必须非空。
   4e. ⏳ **距上次启动至少隔 3 分钟**，再启动一遍同一任务 →
       预期：结果能跑，重复的线索被跳过（数字里有"重复 N 条"之类说明），
       而不是把同一批线索再灌一遍。
       （这一条顺带能验"重复启动"——但两次之间必须隔够时间，否则你是在逼它出错。）
4x. 【养号 · 验「设置生效」这一环（这是本轮最该先做的一步）】
   为什么要先做：养号是目前唯一既有设置项、又有真实执行器的模块。
   如果连养号的参数都不生效，后面评论获客里同样的设置项也不可能有意义。
   4x-a. 到「养号」页：养号时长填 **5–6 分钟**（先别填 60 分钟，验参数不需要跑满）、
         视频停留 8–25 秒、点赞概率 10%，勾选在线账号 → 点「开始养号」。
   4x-b. ⏳ 点完**等 90 秒**再看界面。这 90 秒不要刷新、不要停下来又启动。
   4x-c. 打开这条养号任务的运行日志（或执行历史里点开本次执行）→
         第一行应该是「养号参数：时长 5-6 分钟（本次 X 分 Y 秒），每屏停留 8-25 秒，点赞概率 10%」。
         把你抄下来的页面值逐项对一遍：一致 = 设置生效（这一环节通过）；
         不一致 = **P0 设置不生效**，写清「我设 10%，它写 100%」。
         日志里完全没有这一行 = P1，参数对用户不可见。
   4x-d. 盯 3 分钟点赞次数：按 10% 概率、每条视频停 8–25 秒，3 分钟大约刷 10–20 条，
         正常点赞 **1–2 个**。3 分钟点了 5 个以上 = 概率没生效，P0；
         一个都没点也不算错（概率低是正常的），但若页面设的是 100% 却一个没点 = P0。
         ⚠️ 先看日志里有没有这两句，再下结论：
         ·「本轮所有视频都没定位到点赞控件……这是能力限制不是概率问题」
           → 记 **P1 能力缺失**（平台页面结构问题），不要记成"概率没生效"。
         ·「点了无反应」
           → 说明点到了但平台没认，同样记 P1；软件没有虚报点赞数，属于诚实，不是假成功。
         日志里每轮都会写「点赞 N 次（概率跳过 A、已赞过 B、点了无反应 C、无点赞按钮 D）」，
         这四项加起来应该等于本屏数，对不上就记 P1（计数不可信）。
   4x-e. 等到设定的 5–6 分钟走完 → 预期：状态自己变「已完成」，且浏览/点赞数非空。
         不到 1 分钟就"完成" = 时长参数没生效，P0；跑过头很多也不对，P1。
   4x-f. 万一养号也被直接拒绝启动（弹「执行器未接入」）→ 记 P0：
         养号是写动作里最基础的一个，它都起不来，说明整条写链路没接上。
5. 【写类验证 · 评论获客，本剧本最关键也最危险的一步】新建任务：
   关键词「火锅」、执行账号选在线的那个、视频数 **1**、互动总上限 **5**、
   关注上限 **1**、私信上限 **1**，人设随便填一句 → 保存。
   （视频数就填 1。这一轮是验证"它会不会做事"，不是产线跑量，填多了就是在拿账号冒险。）
   5a. 刷新页面、重新打开 → 预期：每一项原样还在。
   5b. ⏳ 确认距上一次任务结束**至少 3 分钟**，再点启动。
       点完**盯住界面 90 秒**（不是 30 秒——真人写一条评论就要 20–27 秒，
       加上进评论区探测 12–13 秒，30 秒根本还没走到提交那步，你会误判成"没反应"）。
       这 90 秒里不要刷新、不要切页、不要连点。把每种状态变化按时间顺序记下来：
       · 情况 A：弹出「执行器未接入 / 缺少发表评论能力」这类说明，并告诉你该用哪个模块
         → 这是诚实拒绝，标「符合当前基线」，不算 bug。
         但要继续查：执行历史和任务状态里有没有留下"这次被拒绝过"的记录（应该是有的）。
       · 情况 B：显示「运行中」，最后报「已完成 / 已发表 N 条」
         → 记下它说发了几条、发在哪个视频。**等它报完成后隔 30 秒**再去看
         （平台有延迟，立刻看可能还没显示）。
         打开抖音那条视频的评论区，找这句话。找不到 = P0 假成功（软件谎报自己干了活）。
         ⚠️ 只验 1 条就停，验完立刻停止任务。
       · 情况 C：显示「运行中」，然后无解释地变「已完成 / 已停止」，统计全是 0 或空白
         → P1 静默失败（用户完全不知道为什么白等了）。
   5c. 不管哪种情况，都去「评论获客」页看这条任务的统计字段叫什么。
       预期：已发表 / 已互动 / 已触达 / 已评过 / 失败。
       如果这里出现的是「视频数 / 评论数 / 线索数」→ P0 语义错位（把采集冒充成了评论获客）。
   5d. 【如果它真的开始发评论了 —— 只验冷却，验完就停】
       盯住第一条和第二条评论的时间：间隔必须 **≥ 5 分钟（300 秒）**，正常在 365–509 秒。
       · 不到 5 分钟就发第二条 → P0 冷却失效（这是会被封号的节奏）
       · 两条之间完全没有等待、连发 → P0
       验到第二条就够了，立刻点停止。**不要为了"多收集点数据"让它接着跑**——
       每多发一条，这个账号的风险就多一分，而你要验的东西第一条就验完了。
   5e. 停下来之后，等 10 分钟再看这个账号一眼（进它的主页、看有没有验证码提示）。
       预期：正常。若出现验证码/限流提示 → 记 P0，并把时间点写清楚。
   5f. 【改设置 → 重跑，只做一次】把「互动间隔」从 300-600 改成 600-900
       （或把「每个视频点赞数量」从 1-3 改成 1-1），保存、刷新确认数值还在，再启动一次 →
       预期：运行日志里的「生效参数」跟着变。
       设置改了、日志还是老值 = **P0 设置读的是缓存或默认值**，用户改了等于没改。
       ⚠️ 只有它真的开始发评论/点赞时才做这一步；如果它诚实拒绝，就跳过，
       不要为了"测到这一步"去逼它做不该做的事。
6. 实况大屏（只在确实有任务在跑的时候验）：
   6a. 有任务运行时切过去 → 预期：出现该账号的任务卡片（昵称、进度、轨迹日志在滚动），
       画面区出现「DY·账号昵称」的窗口或占位卡片，不允许显示「暂无正在运行的任务」。
   6b. 没有任何任务时切过去 → 预期：显示空态，并且说明"为什么空、该干什么"。
   6c. 任务结束后**不刷新页面，原地等 60 秒** → 预期：卡片自己消失或变成已完成，
       不能一直挂着"运行中"。（这 60 秒就是用来等界面自己收敛的，你一手动刷新，
       就变成"我刷了才正常"——那验不出东西。）
7. 执行历史：左下角入口 → 预期：能看到刚才那几次执行（线索采集那次、评论获客那次都要在），
   每条能看出：哪个任务、什么时候、结果是什么、每轮干了什么。
   点开一条看明细 → 预期：明细和任务页显示的数字一致（对不上就是 P1）。
8. 常驻与托盘（这一段必须真点）：
   8a. 点窗口右上角关闭（不是退出）→ 预期：窗口消失但软件没退出（托盘图标还在）。
   8b. ⏳ 距上一次任务结束**至少隔 3 分钟**，在窗口已关闭的状态下，再启动一次任务 →
       预期：照样能跑（说明常驻没断）。
       （这一步只验"关窗后还能干活"，用线索采集这种读任务就行，不必再跑写任务。）
   8c. 托盘右键，逐项点：打开主界面 / 执行历史 / 显示采集窗口 / 退出 → 每项都要有反应，
       记下点完发生了什么。点「退出」后，软件进程应真正结束（任务管理器里能看到进程消失）。
9. 【多账号，可选 · 建议放在第 5 步之前做】账号池加第二个账号（不登录）→ 用它启动任一任务 →
   预期：明确提示「该账号未登录，请先登录」，或弹出独立登录窗口。
   不允许拿 A 账号的登录态去跑 B 账号的任务（那算越权，P0）。
   （这一步验的是"拦得住"，本来就不该真的发东西，所以安全；但每次点启动之间仍要隔 60 秒。）
10. 【异常，可选 · 建议也放在第 5 步之前】把桌面壳关掉（模拟执行器离线）→ 回界面点启动 →
    预期：明确提示「执行器离线」，排期自动暂停；壳恢复后自动继续。
    不允许无响应、假装启动、或一直转圈。
    ⏳ 壳重启后等 20 秒再点，别在它还没起来的时候连点——那只会测出"连不上"。
11. 全部做完后，输出一份《用户视角体验报告》，并且在报告里附一张【节奏记录表】：
    每个任务实际等了多久、两次启动之间隔了多久、有没有出现过验证码。
    这张表是别人判断"你的结论可不可信"的依据。

【报告格式】（每发现一个 bug 立刻写一条，不要攒到最后）
- 编号 / 严重度：P0 / P1 / P2（定义见下）
- 操作步骤：（精确到点了哪个按钮、填了什么字）
- 预期效果：
- 实际效果：（界面原文 + 截图；如果涉及数字，把两个数字都写出来）
- 复现率：必现 / 偶现（偶现要写明复现了几次中的几次）
- 时间点：（几点几分，以及距上一步隔了多久）——凡是写操作相关的 bug 必须写这一条，
  否则没人判断得出这是软件的问题还是你催出来的风控反应
- 设置值 vs 实际值：（页面填的是 X，运行日志里生效的是 Y；一致就写"一致"）
- 我的感受：（一句话，比如"我以为它在干活，其实什么都没发生"）

【严重度定义】
- P0 丢数据 / 假成功 / 语义错位 / 节奏失控 / 设置不生效：配置保存后丢失、说做了实际没做、
  用 A 模块的动作冒充 B 模块、拿别的账号的登录态跑任务、
  页面设了 A 却按 B 跑（设 10% 点赞跑成条条都点、设 15 分钟跑成 1 分钟）、
  两条评论间隔少于 5 分钟、超过每日配额仍继续跑。
- P1 功能没反应 / 静默失败 / 查不到记录：点了没动静、跑完不给原因、
  执行历史里找不到刚才那次。超过 3 分钟仍在转圈也算这一档。
- P2 提示不友好 / 空态无引导 / 文案歧义：只有"暂无数据"、按钮名看不懂、
  同一条提示出现两次、计时器/倒计时给了却不走。

【最后一步：报告结尾必须写四句话】
1. 我作为新用户，最不敢用的一个功能是哪个，为什么；
2. 如果只能修一个 bug，我选哪个；
3. 有没有哪一步是我"点了但完全不知道会发生什么"的；
4. 这次测试里，我有没有在没等够时间的情况下催过它、催了哪几次、催完之后看到的现象是什么。
   （老实写。催出来的异常不算 bug，但"一催就露馅"的地方往往是真问题的藏身处。）
```

## 三、当前阶段的判定基线（**不看这一节会把已知状态误报成 bug**）

测试前必须先对齐现状，否则报告会充满重复项：

| 模块 | 现在应该是什么表现 | 判为 bug 的情形 |
|---|---|---|
| 评论获客 | 点启动后**明确拒绝**，说明缺少发表评论执行器，指向线索采集 | 显示运行中却什么都不发、或谎报已发表 |
| 养号 | 能真跑：按页面设的时长/停留/点赞概率浏览推荐流，日志首行打印「养号参数」 | 1 分钟就完成、条条视频都点赞、设了概率却从不生效 |
| 线索采集 | 能真跑：搜视频 → 抓评论 → 入库 → 去重 | 搜到 0 条却报"正常完成"、登录墙当成空结果 |
| 评论点赞 / 吞评检测 / 作品发布 | 页面能开，启动按钮不产生任何实际动作 | 页面白屏、报错弹窗、无限转圈 |
| 实况大屏 | 只在有任务真跑时显示卡片；无任务时显示带说明的空态 | 任务在跑却显示"暂无正在运行" |
| 执行历史 | 每次启动（含被拒绝的）都留一条记录 | 跑过却查不到 |
| 托盘 | 关窗不退出、隐藏状态仍能采集 | 关窗即退、隐藏后采集全失败 |
| 互动节奏 | **以页面设置为准**；页面没设时：评论区 5–10 分钟一条、点赞靠概率、每日读 600/赞 150/评论 50/私信 100 | 设了 10% 却条条都点、改设置后日志不变、10 秒连发两条、超配额仍在跑 |

> 这条基线会随版本变化。每次测试前，先问开发者要一份「当前已知状态」，否则"拒绝启动"会被反复当 bug 报。

## 四、剧本每一步对应的真实坑（提示词为什么这么写）

v1 → v2 期间真机踩过的坑，全部转成了剧本里的检查点：

| 剧本条目 | 真实发生过的 bug | 根因 |
|---|---|---|
| 开头「两个模块的区别」 | 评论获客被实现成"读评论→打分→待触达"，跑的是采集指令 | 语义错位（v1 提示词也跟着错，导致误判为"已修复"） |
| 铁律 3「去平台上验」 | 统计说采集了 66 条线索，被当成评论获客跑通 | 用读动作的证据冒充写动作 |
| 5b 情况 A | 修复后启动返回 `executor_not_ready`，但外层 `success:true` | 壳只看外层会误判成功 |
| 5b 情况 C | 事件传 `status=failed` 时界面只显示"任务已挂起"，没有原因 | 壳只在 `finished + finishMessage` 组合下展示原因 |
| 4a / 5a「刷新复核」 | 只传 id 的启动请求把任务记录整条覆盖成空壳 | 启动通道拿传参当记录全量保存 |
| 4e「再跑一遍」 | 同一批线索被重复灌入 | 去重只在入库层，任务层没校验 |
| 6a「大屏卡片」 | 任务在跑，大屏永远"暂无需要监控的窗口" | 四个数据通道只认旧引擎，看不见新引擎 |
| 6b「空态说人话」 | 大屏空屏没有任何解释 | — |
| 7「执行历史」 | 评论获客 7 次运行全部缺席，任务 stats 全 0 | 引擎没接生命周期记录 |
| 8a「关窗不退」 | 关窗即退出、孤儿后端、无自启 | 没有托盘与退出钩子 |
| 9「多账号」 | 任务按 accountId 开独立分区，老登录态在默认分区 → 弹登录墙，报"正常完成 0 条" | 分区迁移没做绑定 |
| 11「同一动作两遍」 | 出现 53ms 幽灵运行记录（关键词还是旧值） | 保存与启动竞态 |
| 4x「养号参数对账」 | 页面设 60–120 分钟、点赞 10%，实际跑 1 轮 6 屏、0 点赞；养号一启动就被「执行器未接入」拒绝 | runner 只认 `cycles/dwellMs/likeMax`（页面传的是 `nurtureDurationMin/stayMin/nurtureLikePercent`）；`start-task` 被统一塞进评论获客门禁 |
| 10「执行器离线」 | 壳离线时排期仍照跑，全部失败刷屏 | 没有离线宽限与自动暂停 |

**核心思想**：让 AI 扮用户，最值钱的不是"会点按钮"，而是三条纪律 ——
**不脑补界面、不信自称成功（要外证）、数字要对账。**
假成功类 bug 只能靠"刷新复核 + 外部取证 + 对账"抓出来，靠"看有没有报错"永远抓不到。

## 五、怎么用这份提示词（实操建议）

1. **拆场次跑，而且要比以前更慢。** 建议拆成三场：
   ① 走查 + 线索采集（约 20 分钟，含两次启动之间的 3 分钟等待）
   ② 评论获客 + 大屏 + 执行历史（**约 40 分钟**——因为要真的等 5–10 分钟看冷却，
   不能为了快把冷却验成"没等待"）
   ③ 常驻 / 托盘 / 多账号 / 离线（约 20 分钟）
   跑太久 AI 会开始"记忆式编造"，所以宁可分三天跑，也不要一天跑完。
2. **要求它每步截图。** 没有截图的"我看到…"一律不可信——它可能在根据界面结构猜。
3. **写操作必须有人在场，且一次只跑 1 条。** 第 5 步一旦真发评论是留痕的；
   验到第二条评论、确认冷却间隔够，就立刻停。
4. **报告要交叉核对。** AI 说"执行历史里有记录"，就自己去点一次；它说"已发表成功"，就去平台看。
   AI 的报告是线索，不是结论。
5. **不要用开发者视角提问。** 别问"是不是 ipc 通道没聚合"，要问"你点了之后屏幕上出现了什么"。
   问题里带技术词，AI 会自动替软件解释。
6. **两轮对比更有效。** 修完 bug 后用**同一份提示词**再跑一遍，只对比"上一轮失败的步骤这次过没过"。
7. **节奏比覆盖率重要。** 宁愿这次只测完第 1–4 步、每步都等够了，也不要三小时跑完全流程
   却全程在催。催出来的现象没有诊断价值，还会让账号进入风控冷却，把后面几天的测试全废掉。
8. **同一天不要重复用同一个账号测写操作。** 一轮写操作测试之后，让这个账号至少静置到第二天。

## 七、设置项与参数出处（页面字段 → 后端读哪里 → 在哪生效）

> 这张表是用来回答「我在页面上设的东西，后端到底认不认」的。左边是你眼睛看到的，
> 中间是代码读的字段名，右边是它真正起作用的地方。名字对不上 = 设了也没用。

| 页面设置项（用户看到的） | 配置字段（前端传的） | 后端读取位置 | 真正生效的地方 |
|---|---|---|---|
| 养号 · 养号时长（分钟） | `nurtureDurationMin/Max` | `runtime/runners.py` `run_warmup` 的 `_pair(...)` | 到点自然结束（不再固定 1 轮） |
| 养号 · 视频停留（秒） | `stayMin/stayMax` | 同上 | 下发 `warmup-watch.dwellMs`（每条视频随机取） |
| 养号 · 点赞概率（%） | `nurtureLikePercent` | `_pct(...)` | 下发 `likeProbability`，壳内每屏掷骰 |
| 监控 · 检查间隔（秒） | `intervalSecondsMin/Max`（兼容 `intervalMin/Max`） | `run_monitor` 的 `_pair(...)` | 每轮重新随机取间隔 |
| 评论获客 · 互动间隔（秒） | `intervalMin/intervalMax` | ❌ 未读取 | 执行器未接入（见下） |
| 评论获客 · 每视频点赞数量 | `likeMin/likeMax` | ❌ 未读取 | 执行器未接入 |
| 评论获客 · 点赞概率（视频） | `mainVideoLikePercent` | ❌ 未读取 | 执行器未接入 |

**评论获客那几个字段为什么是"未读取"**：评论获客是写动作（发表主评 + 对评论者点赞/回复/关注/私信），
桌面壳目前只提供读类指令（搜索、采评论、读主页、养号浏览），没有 `post-comment` / `like-comment`。
所以后端在启动时**诚实拒绝**并留证据，页面上填的间隔和数量只被保存、不会被执行。
这不是"设置生效了但效果慢"，是"根本没做"。报告里遇到它拒绝，标「符合当前基线」，不是 bug。
